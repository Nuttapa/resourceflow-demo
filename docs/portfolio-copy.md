> **ส่วนนี้เขียนเสร็จแล้ว** ทุกข้อความต่อไปนี้อิงจากสิ่งที่พิสูจน์ได้จากโค้ดในโฟลเดอร์นี้

## B.2 Short description — resume bullet / project card

**One line (resume):**

> Built ResourceFlow, an independent frontend-only demo of a server-resource request, approval and allocation workflow — role-based permission rules, state-machine transitions and derived capacity accounting, covered by 254 unit tests.

**Two to three lines (project card):**

> An independently built portfolio demonstration of how a shared compute cluster hands out resources: students file requests, approvers decide them, administrators allocate and later release capacity, and every action — including every refused one — lands in an audit trail. The workflow and permission rules live in a pure TypeScript layer with no React in it, so the behaviour is unit-tested rather than merely demonstrated. Simulated data only; no backend, no database and no real system behind it.

## B.3 Full portfolio description

> ResourceFlow is a self-contained demonstration of a server-resource workflow: a request is filed,
> approved or rejected, allocated from a shared pool, then returned or expired. I built it on my own
> as a portfolio piece, and it runs entirely in the browser — there is no backend, no database and
> no connection to any production system.
>
> The point of the project is not the screens. It is that the rules sit in one place and can be
> proven. Permissions, status transitions and capacity arithmetic live in a pure TypeScript layer
> that imports no React and touches no DOM, so each rule is exercised directly by unit tests. The
> user interface can only ask for a change through a single dispatch function; it never edits a
> request, an allocation or a pool itself. A screen decides what to draw by calling the same
> permission function the workflow uses to decide what to allow, so a list can never show an action
> that a direct attempt would refuse.
>
> Three design decisions carried most of the weight. First, every action returns a result rather
> than throwing, and a refused action still produces an audit entry while leaving the data
> byte-for-byte unchanged — refusals are evidence, not silence. Second, capacity is derived, never
> stored: usage is recomputed from the allocation records on every read, so returning or expiring an
> allocation cannot drift out of step with the pools. Third, the clock and identifier generation are
> injected, so tests run against a fixed clock and sequential ids and assert exact values instead of
> approximations.
>
> **Portfolio Demo — Simulated data only. Not connected to any real system.** All users, email
> addresses and resource figures in the demo are fictional. The role selector is a simulated session
> for demonstration purposes — there is no password, no token and no identity provider anywhere in
> the application, and the permission checks run in the browser. They model how authorisation should
> be structured; they are not production security, and a real system would enforce the same rules on
> a server.

## B.4 Key features

- **Full request lifecycle** — create, approve or reject with a mandatory reason, cancel, allocate, return, and administrator-forced expiry, with a status timeline per request built only from recorded data.
- **Role-based permissions** — three simulated roles (Requester, Approver, Administrator) resolved through one pure `can(actor, action, context)` function used by both the UI and the workflow.
- **Separation of duties** — holding the Approver or Administrator role does not let you decide a request you filed yourself; the rule is enforced in the workflow, not by hiding a button.
- **Generated permission matrix** — the Roles screen builds its table by calling the real permission function for every role at render time, and evaluates ownership-dependent rules as separate cases so no cell can be misread as unconditional.
- **Derived capacity accounting** — pool usage is `baseline + active allocations`, recomputed on every read; allocation is refused when a pool has no room, and capacity can never go negative or exceed the total.
- **Audit trail** — every successful and every refused action is recorded with actor, role, action, target, outcome and reason, and the log is filterable by role, outcome, target type and action.
- **Validation and honest error handling** — form input is validated for display and re-validated by the workflow before anything is stored; a success message appears only when the action was both applied and persisted.
- **Storage recovery** — stored data is validated for shape, value domains, id uniqueness, referential integrity and capacity arithmetic; damaged data is backed up before anything is overwritten, and if the backup cannot be written the original bytes are left untouched.
- **Accessible, responsive interface** — keyboard-operable dialogs with focus management, labelled form controls with announced errors, tables that become cards on narrow screens, and status conveyed by text as well as colour.

## B.5 Technical stack

| Area | Choice |
|---|---|
| Framework | Next.js 16.4.0 (App Router, static export) |
| UI | React 19.3.0, Tailwind CSS 3.4.19 |
| Language | TypeScript 5.9.3 (`strict`, `noUncheckedIndexedAccess`) |
| Testing | Vitest 5.0.4 — 254 tests across 17 files |
| State | React context over a pure rule layer; persistence in `localStorage` with a versioned schema |
| Runtime dependencies | three: `next`, `react`, `react-dom` — no UI kit, no state library, no date library, no icon package |

Architecture in one line: `src/lib/` holds types, validation, permissions, the workflow state machine, capacity, audit and storage — none of it imports React; `src/state/` binds that layer to the UI; `src/components/` and `src/app/` only read and dispatch.

## B.6 What I learned / skills demonstrated

- **Separating business logic from presentation.** Keeping React out of the rule layer is what made the rules testable; it also meant the permission logic could not quietly fork into "what the screen allows" and "what the system allows".
- **Modelling a state machine explicitly.** A single transition table decides every status change, so skipping a step is refused by construction rather than by scattered conditionals.
- **Authorisation design.** Writing one permission function with machine-readable denial codes and human-readable reasons, then reusing it for both rendering and enforcement — and learning why separation of duties has to be checked on the actor, not the role.
- **Data integrity over convenience.** Choosing to derive capacity instead of storing a running total removed a whole class of drift bugs, at the cost of recomputing on every read.
- **Defensive handling of untrusted stored data.** Treating `localStorage` as data that may be corrupt, unreadable or unwritable, and deciding what the application must *not* do when it cannot preserve what it found.
- **Testing what matters.** Writing assertions for the refusals — that a denied action changes nothing and still leaves evidence — rather than only for the happy path.
- **Honest interface feedback.** Never reporting a save that was not observed to succeed.

## B.7 Limitations and scope

Stated plainly, because they are part of the design rather than gaps I overlooked:

- **Frontend only.** No backend, no database, no API routes, no server actions. The application is a static export.
- **Not authentication.** The role selector switches a simulated persona. There is no password, token or identity provider, and the permission checks run in the browser, where a user could bypass them with developer tools. They demonstrate authorisation *modelling*; production enforcement belongs on a server.
- **Not a security-certified system.** Nothing here has been audited or certified, and it should not be read as a security product.
- **Hosted as a static site, with nothing behind it.** This portfolio demo is hosted on Vercel at https://resourceflow-demo.vercel.app/ and runs entirely in your browser. It uses simulated data and does not connect to any real system or backend — hosting a static export does not make it a production system.
- **Data is per browser.** State lives in one `localStorage` key and never leaves the machine; clearing site data resets the demo.
- **UI behaviour is verified manually.** Unit tests cover the rule layer. Dialog focus handling, screen-reader announcements and responsive layout were checked by hand, not by automated browser tests.
- **Fictional data.** Every user, email address (`@example.com`) and resource figure is invented for the demo.

## B.8 Suggested interview talking points

Each of these is backed by something you can open in the code, which is the whole point.

1. **"Why is the logic in a folder with no React in it?"** — Because it made the rules testable and kept a single source of truth. Offer to show `src/lib/workflow.ts` beside a test file.
2. **"Show me a rule that the UI cannot bypass."** — Self-approval. The button is not rendered, *and* the workflow returns `SELF_APPROVAL` if the action arrives anyway. There is a test for the second part specifically.
3. **"What happens when something is refused?"** — Nothing changes, and an audit entry is written. Mention the test helper that deep-compares all business data after every refusal.
4. **"How do you know capacity never drifts?"** — It is derived, not stored. The round-trip test asserts every pool returns to its exact starting value after create → approve → allocate → return.
5. **"How do you handle corrupt stored data?"** — Validate four layers, back up before overwriting, and refuse to overwrite at all when the backup fails. This is a good place to talk about failing safe.
6. **"Your dependency audit shows vulnerabilities — why not fix them?"** — They are build-time development dependencies of Tailwind 3, not shipped to users, and the only offered fix is a major-version upgrade. Explaining a reasoned decision not to act is worth more than a clean number.
7. **"What would you change to make this real?"** — Move the rule layer behind an API and enforce it server-side, replace the persona switcher with real authentication, make the audit log append-only storage you cannot edit, and add integration tests around the API.
8. **"What is the difference between this and your team project?"** — Keep this answer crisp and rehearsed. This is an independent mockup you built alone to demonstrate the concepts; the team project is separate work with its own scope and your own specific contribution. Never let the two blur together.
